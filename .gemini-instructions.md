# Gemini Instructions for Magical Inventory UI

You are an expert AI assistant for an Angular project using TypeScript. Your primary goal is to help me write clean, maintainable, and high-quality code that adheres to the project's established conventions and best practices.

## Project Overview

- **Framework:** Angular (Standalone Components)
- **State Management:** NgRx SignalStore for feature state, and Signals for local component state.
- **UI Components:** PrimeNG (based on `preset.prime.ts` file)
- **Styling:** CSS with separate files per component.
- **Package Manager:** pnpm

## General Principles

- **Adhere to Existing Code:** Your top priority is to match the style, structure, and patterns of the existing codebase.
- **Strict Typing:** Always use strict type checking. Avoid `any` and prefer specific types or `unknown` when necessary.
- **Linting and Formatting:** All code must adhere to the rules in `.eslintrc.mjs` and `.prettierrc`.

## Angular Best Practices

- **Standalone by Default:** All new components, directives, and pipes must be standalone. Do not use NgModules.
- **`input()` and `output()`:** Use the `input()` and `output()` functions instead of `@Input()` and `@Output()` decorators.
- **OnPush Change Detection:** Always use `changeDetection: ChangeDetectionStrategy.OnPush` for components.
- **Host Properties:** Use the `host` property within the `@Component` or `@Directive` decorator instead of `@HostBinding` and `@HostListener`.
- **`NgOptimizedImage`:** Use `NgOptimizedImage` for all static images.
- **Control Flow:** Use the new built-in control flow (`@if`, `@for`, `@switch`) in templates instead of `*ngIf`, `*ngFor`, and `*ngSwitch`.
- **Services:** Services should be provided in root (`{ providedIn: 'root' }`) and use `inject()` for dependency injection, not constructor injection.
- **Forms:** Always use Reactive Forms for handling user input, not template-driven forms.
- **Style Bindings:** Use `[class]` and `[style]` bindings instead of `ngClass` and `ngStyle`.

## State Management with NgRx SignalStore

This project uses NgRx SignalStore for managing feature-specific state.

- **Structure:** Follow the existing pattern for creating stores (e.g., `categories.store.ts`). A store should include:
    - A state interface.
    - An initial state object.
    - The `signalStore` definition.
- **`withState`:** Use `withState` to define the shape of the store's state.
- **`withReducer`:** Use `withReducer` and `on(...)` to define state changes in response to events. Reducers must be pure functions.
- **`withEffects`:** Use `withEffects` for handling side effects, such as API calls. Effects should listen for events, call services, and dispatch new events (success or failure).
- **Events:** Define events in a separate file (e.g., `events/category-api-events.ts`) to be used in reducers and effects.
- **Component State:** For local state within a component that is not shared, use `signal()`, `computed()`, and `effect()`.

## Component Structure

- **File-per-Concern:** Components have their logic (`.ts`), template (`.html`), and styles (`.css`) in separate files.
- **Small Components:** Keep components small and focused on a single responsibility.
- **Smart/Presentational:** Follow a smart-container/presentational-component pattern where appropriate. Page components (e.g., `category-list-page.ts`) are often smart components that interact with the store, while child components (e.g., `categories-table.ts`) are presentational and receive data via inputs.

## Tooling

- **pnpm:** Use `pnpm` for all package management. For example: `pnpm install`, `pnpm start`, `pnpm test`.
- **Commits:** Follow conventional commit standards for commit messages.
